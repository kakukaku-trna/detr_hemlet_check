## 🚀 三种使用方式

### 方式一：快速开始 (10分钟)

**目标**: 快速了解优化选项和预期收益

**步骤**:
1. 打开 `快速参考.md`
2. 选择适合你的方案 (A/B/C)
3. 复制对应的命令行参数
4. 运行基准测试

**时间**: ~10 分钟
**输出**: 性能对比表

---

### 方式二：系统优化 (1-2 周)

**目标**: 深入理解模型并进行系统优化

**完整流程**:

#### 📊 第一步：分析 (使用 `prompts/analyze.md`)

```
任务: 分析当前 Deformable-DETR 实现
步骤:
1. 读完 analyze.md
2. 准备你的模型配置
3. 问 Claude:
   "基于我的 Deformable-DETR 配置文件，请进行以下分析：
   - 参数分布 (按组件)
   - FLOPs 分布
   - 内存使用情况
   - 优化机会排序 (按 ROI)
   参考 prompts/analyze.md 中的框架"

输出: 
- 当前架构总结
- 分析表格
- 优化候选排序
- 推荐起点
```

**预期时间**: 30 分钟  
**输出**:
- 参数/FLOPs 分布表
- 优化机会排序
- ROI 评分

---

#### 🔧 第二步：优化规划 (选择方向)

基于分析结果，选择优化方向：

```
推荐顺序:
1️⃣  Backbone 替换 (最大收益)
2️⃣  Decoder 层数减少 (简单有效)
3️⃣  Query 压缩 (快速验证)
4️⃣  Attention 简化
5️⃣  知识蒸馏 (精度恢复)
6️⃣  部署优化 (推理加速)
```

## 📊 Prompt 详解

### Prompt 1: analyze.md - 分析当前实现

**何时使用**: 
- 开始优化前
- 需要理解模型结构和瓶颈

**输入**:
```
- 模型配置文件
- 当前的 mAP 基准线
- 硬件信息 (GPU 型号等)
```

**输出**:
```
- Backbone 信息 (参数、FLOPs、通道数)
- Encoder 分析 (层数、复杂度)
- Decoder 分析 (层数、Query 数等)
- Attention 分析 (头数、采样点)
- 参数分布表 (各组件占比)
- FLOPs 分布表
- 优化机会排序表 (ROI 评分)
```

**示例使用**:

```markdown
请分析我的 Deformable-DETR 实现。

当前配置:
- backbone: resnet50
- num_encoder_layers: 6
- num_decoder_layers: 6
- num_queries: 300
- num_heads: 8
- hidden_dim: 256

基准性能:
- mAP: 42.5
- 延迟: 45ms
- 参数: 43.3M

请提供:
1. 参数分布表 (各组件占比)
2. FLOPs 分布表
3. 潜在的优化机会排序 (按 ROI)
4. 推荐的优化起点
```

1. 需要修改的文件列表

### Prompt 3: benchmark.md - 基准测试

**何时使用**:
- 修改完成后
- 需要性能评估

**输入**:
```
- 修改前后的配置
- 基准线性能数据
- 硬件信息
```

**输出**:
```
- 对比表格 (参数/FLOPs/延迟/mAP)
- 性能曲线分析
- ROI 评分
- 建议 (是否值得采用)
```

**示例使用**:

```markdown
请基准测试这个优化。

修改: Query 压缩 (300→100)
修改前配置: num_queries=300, ...
修改后配置: num_queries=100, ...

基准线:
- 参数: 43.3M
- FLOPs: 150G
- 延迟: 45ms
- mAP: 42.5

请提供对比:
1. 详细的性能表格
2. 百分比变化
3. ROI 评分 (收益/成本)
4. 是否推荐采用

参考 prompts/benchmark.md 的格式
```

## 📝 模板详解

### Template 1: experiment.md - 实验记录

**用途**: 记录单个优化实验的全过程

**包含内容**:
```
- 实验 ID 和日期
- 假设和预期收益
- 基准线和修改配置
- 实施细节
- 基准测试结果
- 对比分析
- ROI 评分
- 后续步骤
- 经验总结
```

**使用流程**:

1. **复制模板**
```bash
cp templates/experiment.md experiments/exp_20260610_query_compress.md
```

2. **填写实验信息**
```markdown
| 字段 | 值 |
| 实验ID | 20260610-query-compress-100 |
| 日期 | 2026-06-10 |
| 优化类型 | Query 压缩 |
| 状态 | In Progress |
```

3. **填写配置信息**
```python
# 基准线配置
num_queries = 300
...

# 修改后配置
num_queries = 100
...
```

4. **填写测试结果**
```
| 指标 | 基准线 | 修改后 | 变化 |
| 参数 (M) | 43.3 | 43.3 | 0% |
| FLOPs (G) | 150 | 123 | -18% |
| 延迟 (ms) | 45 | 38 | -15% |
| mAP | 42.5 | 41.8 | -0.7 |
```

5. **分析 ROI**
```
ROI 评分: 
- 速度提升: ⭐⭐
- 精度保留: ⭐⭐⭐
- 实施复杂度: ⭐
- 总体推荐: 是
```

---

### Template 2: ablation.md - 消融研究

**用途**: 系统性理解多个优化的交互效应

**设计流程**:

1. **定义研究对象**
```
研究对象: Query 数量、Decoder 层数、采样点数 的组合效应
```

2. **设计实验组合**
```
| Config | Query | Dec_L | Sampling | 参数 | FLOPs | mAP |
| 基准线 | 300   | 6     | 4        | 43M  | 150G  | 42.5|
| 实验1  | 200   | 6     | 4        | 43M  | 140G  | 42.3|
| 实验2  | 300   | 5     | 4        | 40M  | 120G  | 41.8|
| 实验3  | 300   | 6     | 2        | 43M  | 135G  | 42.1|
| ...    | ...   | ...   | ...      | ...  | ...   | ... |
```

3. **分析交互效应**
```
Query + Decoder:
- 单独: Query 300→200 (-5%), Decoder 6→5 (-15%)
- 组合: 是否 > -20%? (线性?) 还是有协同?

Query + Sampling:
- 单独: Query 300→200 (-5%), Sampling 4→2 (-10%)
- 组合: 效果?
```

4. **得出结论**
```
关键发现:
1. Query 和 Decoder 的效应大致独立
2. Sampling 点数对不同 Query 数量的影响不同
3. 最优组合: Query=150, Decoder=4, Sampling=2
```

## 💡 最佳实践

### 1. 系统化优化

**❌ 错误做法**:
- 一次修改多个参数
- 没有基准线对比
- 不记录实验过程

**✅ 正确做法**:
- 逐个优化，记录每一步
- 始终对比基准线
- 使用模板记录所有细节

### 2. 消融研究

**✅ 推荐流程**:
```
第1周: 单个优化验证 (Query / Decoder / Sampling)
第2周: 组合优化验证 (两两组合)
第3周: 最优配置确认 + 知识蒸馏
第4周: 部署优化 (ONNX/TensorRT)
```

### 3. 基准测试

**✅ 标准做法**:
```
1. 预热 100 次迭代 (排除冷启动)
2. 测试 100+ 次迭代，记录平均值和标准差
3. 在目标硬件上测试
4. 记录完整的硬件/软件信息
5. 多次运行取平均值 (减少随机波动)
```

### 4. 文档记录

**✅ 记录要点**:
- 每个实验记录在单独的文件
- 包含完整的配置和结果
- 附上 ROI 分析
- 记录失败的尝试 (便于后人学习)

## 🔄 工作流示例

### 完整示例：Query 压缩优化

**Day 1: 分析和规划**

```
1. 使用 analyze.md
   输入: 当前配置
   输出: 优化机会排序，Query 在前3
   
2. 决定优化方向
   选择: Query 压缩 (简单，收益中等)
   
3. 使用 optimize.md
   输入: Query 300 → 100
   输出: 代码修改方案
```

**Day 2-3: 实施和测试**

```
1. 修改代码 (按 optimize.md 的建议)
2. 运行 fine-tune (10-20 epochs)
3. 评估 COCO 验证集上的 mAP
4. 使用 benchmark.md 进行性能测试
5. 记录结果到 experiment.md
```

**Day 4: 分析和决策**

```
1. 对比基准线
   参数: 0% (无变化) ✓
   FLOPs: -18% ✓
   延迟: -15% ✓
   mAP: -0.7 ⚠️ (可接受)
   
2. ROI 评分
   收益: 高 (15% 速度)
   成本: 低 (代码改动少)
   风险: 低 (精度损失在接受范围)
   
3. 决策: 采用这个优化 ✓

4. 计划下一步
   - 结合其他优化 (Decoder 减层)
   - 或转向 Backbone 替换
```

## ❓ 常见问题

### Q: 我应该从哪个优化开始？
**A**: 建议顺序：
1. Query 压缩 (最简单，快速验证框架)
2. Decoder 减层 (简单，收益显著)
3. Backbone 替换 (复杂，收益最大)

### Q: 需要多长时间？
**A**: 
- 单个优化: 1-2 天
- 消融研究: 1-2 周
- 完整优化 + 部署: 3-4 周

### Q: 如何处理 mAP 下降？
**A**: 
- 降幅 < 0.5: 可接受，直接采用
- 降幅 0.5-1.0: 使用知识蒸馏恢复
- 降幅 > 1.0: 重新评估方案或组合优化

### Q: 知识蒸馏一定要做吗?
**A**:
- 快速优化: 不需要
- 生产部署: 建议采用 (可恢复 0.5-1.5 mAP)
- 追求极限性能: 必须做
